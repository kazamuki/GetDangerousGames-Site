# Get Dangerous Games — Site Rebuild

## What this is

The Get Dangerous Games home site (previously live at GetDangerous.net) was originally built in Google Sites. This repo is where it's being rebuilt as a proper, hand-designed website instead. This file is the map: what exists, where the old content lives, what the brand rules are, and what's still an open decision.

Sibling/related project: **Shadows RPG** (the TTRPG referenced throughout this site, shadowsrpg.com) shares the same brand guidelines but is a separate product with its own Core Rulebook — this repo is scoped to the Get Dangerous Games site only.

**Light mode toggle (2026-09-07):** the site shipped dark-mode-only; Ken asked for an opt-in light mode, built as a **portable token/toggle system meant to be dropped into the sibling Shadows RPG and Character Sheet repos too**, not a one-off local hack. Three new files carry the whole mechanism and are designed to be copied verbatim into those repos (each has a header comment saying so): `assets/css/theme.css` (brand color constants + a semantic token layer — `--bg-page`, `--card-bg`, `--text-primary/secondary/tertiary/faint`, `--accent-cyan/green/gold/magenta`, etc. — defined once under `:root` for dark and again under `:root[data-theme="light"]`, plus the `.theme-toggle` button's CSS), `assets/js/theme-init.js` (blocking, no-dependency script that reads `localStorage.getItem('theme')` and sets `html[data-theme]` *before* the stylesheet `<link>` tags in `_layouts/default.html`'s `<head>` — that ordering is what prevents a dark→light flash on load), and `assets/js/theme-toggle.js` (deferred; wires up the header's sun/moon button, persists the choice, updates `aria-pressed`). Because getdangerous.net, shadowsrpg.com, and the Character Sheet app are separate domains, `localStorage` is origin-scoped — shipping the same files to all three makes them behave identically and each remembers that visitor's choice on that site, but a choice made on one site can't automatically follow to another (no shared backend/cookie-domain trick was built for this).

The light palette isn't new colors — it's the existing 8 brand colors reassigned, backed by real WCAG contrast math (not guessed): Static Cyan/Signal Gold/Ghostly Green — the three colors the "Brand-color consistency pass" note above proved work well as *text* against the dark Midnight background — all fail badly as text against a light background (1.28–2.35:1, nowhere near the 4.5:1 minimum), while Aether Pulse/Deep Circuit (and Neon Veil at large-text sizes only) pass comfortably (7–10:1). So in light mode, Deep Circuit and Aether Pulse take over every eyebrow/link/icon-accent role that cyan/gold/green used to fill — it's the exact mirror image of the dark-mode reasoning already documented above, not a new decision. Per-story accent colors (`_stories/*.md`'s `accent` front matter, used inline as `--story-accent`) get a `color-mix(in srgb, var(--story-accent) 65%, black 30%)` darkening in light mode via a new `--story-accent-safe` token (`.story-article`/`.story-card` in `theme.css`) — reuses the `color-mix` idiom `.status-badge`'s `--badge-tint` already established, so all 7 stories stay legible without hand-picking new hex values per story.

**Scoping call, worth knowing if extending this later:** photo-backed bands (`.hero`, `.page-header`, `.shadows-band`, `.story-header`, `.spotlight-strip`) keep their dark scrim treatment near the photo — the top/middle gradient stops (`rgba(13,23,49,0.35-0.6)`) stay fixed in both themes so white overlay text is always legible over the photo — but the gradient's *final* stop now blends into `var(--bg-page)` rather than a literal `var(--midnight)` (see the Ken-review fixes paragraph below for why). Only chrome (header/footer/nav), cards, prose, and non-photo sections otherwise flip with the toggle. One consequence: `.status-badge` (used both inside the always-dark `.story-header` and on the theme-aware `.story-card` grid) needed a `.story-header .status-badge` override pinning it back to a white-mix tint, since the general rule's `--badge-tint` mixes toward `var(--text-primary)` (which itself flips) — see the comments around both rules in `main.css` before touching either.

### Local dev environment (Ruby)

Ruby 4.0.6 + Devkit installed 2026-09-05 to `C:\Ruby40-x64` (via RubyInstaller). Two non-obvious
things had to be fixed to get `bundle exec jekyll serve` working locally — both already fixed in
the repo, documented here so nobody "fixes" them back to the naive version later:

1. **`github-pages` pins ancient gems** (Jekyll 3.9.0, Liquid 4.0.3 — matching GitHub's own frozen
   Pages build environment) that assume things modern Ruby removed: `webrick`/`csv`/`logger`/
   `base64`/`bigdecimal` left Ruby's default gems over several versions (added explicitly to the
   Gemfile), and Liquid still calls Ruby's fully-removed taint methods (`String#tainted?` etc.) —
   fixed with a shim **in the Gemfile itself**, not a `_plugins/` file (github-pages forces Jekyll's
   `safe` mode, which disables custom plugins entirely — the shim has to run before that even
   matters). The shim must use `::Object.class_eval` rather than `class Object ... end` — the
   latter silently reopens a shadow class nested inside Bundler's own Gemfile-eval context instead
   of the real top-level `Object`, so it looks like it worked but doesn't.
2. **None of this affects the real GitHub Pages build** — confirmed by polling the Pages build API
   after every push in this session; GitHub builds on its own older Ruby where these methods still
   exist. This is purely a "modern Ruby running 2019-era gems" local problem.
3. **`.claude/launch.json`'s `jekyll-site` config runs through `cmd.exe /c` with an explicit
   `PATH=C:\Ruby40-x64\bin;%PATH%` prefix**, not a bare `bundle`/`ruby` call. Two independent
   Windows gotchas forced this: the preview tool's process spawner can't invoke `.bat` files
   without a shell, and `ruby -S bundle` (needed instead of a literal path to the `bundle` script —
   the literal-path form triggers a separate RubyGems bin-resolution bug that manifests as a
   misleading `bundler: command not found: jekyll`) needs Ruby's bin dir on `PATH` to find `bundle`
   at all, which isn't guaranteed for a freshly spawned process on this machine.

If `bundle exec jekyll serve` ever breaks again with `command not found: jekyll`, don't trust that
message — run with real args to see the underlying exception (`ruby.exe -S bundle exec jekyll build`
without swallowing stderr) before assuming gems are missing.

## Brand guide summary

Full detail in [brand/theme.md](brand/theme.md). Key points:

- **Palette:** Aether Pulse (violet `#712B8C`), Deep Circuit (tech-blue `#203F7B`), Neutral Zone (`#E7E7E7`) as primary; Neon Veil (`#BC489A`), Midnight Underpass (`#0D1731`), Signal Gold (`#F2C94C`) as secondary; Static Cyan (`#1BBBC4`) and Ghostly Green (`#71C388`) as sparing accents.
